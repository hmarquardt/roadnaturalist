# Road Naturalist architecture

Road Naturalist finds **road corridors** worth researching for wildlife exploration. A corridor is a named candidate with a stable ID, road geometry, status, evidence trail, access finding, and unresolved questions. Future analysis divides that line into segments and evaluates buffers (for example 250 m, 500 m, 1 km) against habitat, water, terrain, protected land, and ecological regions. Tiles and partitions are storage details, not the domain object.

The browser remains a static ES-module application. No runtime framework or build step is required. Source-specific records do not reach UI components. DuckDB-WASM and Spatial initialize only after corridor geometry or ecology is requested; the engine and SQL stay inside `src/gis`, and every road-data path comes from the manifest. Occurrence distance measurement also runs through `src/gis` (`occurrence-query.js`), so a second geometry engine never appears. The UI receives canonical GeoJSON roads/corridors and normalized occurrence summaries, never DuckDB rows or source payloads. Public occurrence APIs are called only on explicit user request, with a bounded request budget, an in-session cache, and no credential in the browser. The Investigator follows the same rule for its own sources: no access research happens on load or on a corridor switch, OpenStreetMap queries are bounded, spaced, and cached, and official-site probes go through the Worker boundary when a deployment provides one (a probe id in, normalized facts out — never a client-supplied URL) or replay the reviewed operator capture when it does not (marked *replayed/deferred*, with `access-verification` coverage `PARTIAL`). AI remains outside the running app; the only model-shaped hook can attach annotation text and cannot set a finding.
Access is a distinct evidence class with its own vocabulary, source-reliability classes, guardrail rules, and coverage dimension. `src/investigator/access.js` decides findings deterministically; `src/investigator/bundle.js` exports a versioned, credential-free, summarized corridor evidence bundle. See [docs/INVESTIGATOR.md](INVESTIGATOR.md).

The regional data plane is published as a spatial catalog plus immutable versioned GeoParquet partitions. The
current window is `or-sw-wa-portland-v2`: about 180 x 180 km around the original pilot, 130 cells of 0.2
degrees, 20 pinned TIGER county archives, Oregon **and** Washington NWI, 23 NHD HR basins, and EPA ecoregions
for both states unioned per level. The earlier slice stays published under its own version and is never
rewritten. Empty cells are declared and answered as typed empty relations; a search that only partly
overlaps the published window runs and reports PARTIAL; a search whose road groups reach the window edge
reports road coverage PARTIAL rather than FULL. Scale limits and the measured decision are in
[docs/REGIONAL-DATA.md](REGIONAL-DATA.md).

Three geometry roles stay separate, and the distinction is load-bearing: **source geometry** (TIGER/Line as published) is never edited; **canonical corridor geometry** is what the application composes, draws, and reports length from; and **analytical geometry** is what the spatial engine is actually given — the canonical line unless the engine refuses to buffer it, in which case it is a point-set-preserving rewriting that is recorded in the result's provenance. One module decides this for the survey, the detailed habitat analysis, and ecoregion overlap, so the two paths cannot disagree about the same corridor. See [docs/DISCOVERY.md](DISCOVERY.md#analytical-geometry-repair).

Three road concepts stay separate: a **source road feature** (one agency record), a **normalized road** (composed, deduplicated geometry with reported gaps), and a **candidate corridor** (one or more roads plus evidence, questions, and coverage). See [docs/ROADS.md](ROADS.md).

A fourth concept sits in front of them: a **discovery corridor** (`src/discovery/units.js`, `segment.js`) is a named road in one place, divided into inspectable lengths when it is long, carrying measured road/wetland/hydrography/ecoregion facts and explicit coverage. Discovery corridors are lightweight; promoting one builds an ordinary candidate from the same road and candidate builders, so there is only ever one kind of detailed candidate. Discovery runs no occurrence query and no access research: those begin after a person promotes a corridor. See [docs/DISCOVERY.md](DISCOVERY.md).

The road/corridor catalog and the Investigator probe catalog are separate on purpose. A road may exist in Road Naturalist with no reviewed official source declared for it, and that is the expected state for a discovered corridor: access stays `UNVERIFIED` and the panel says no reviewed source is declared. Only the probe catalog's declared corridors may carry Investigator sources. See [docs/INVESTIGATOR.md](INVESTIGATOR.md).

## Evidence and authority

Deterministic GIS/data results are authoritative for spatial relationships, dataset coverage, occurrence facts, and scores. Every future analytical result should include dataset ID/version, source URL or citation, build method, query parameters, timestamp where relevant, and the calculation used. Results distinguish `FULL`, `PARTIAL`, `NONE`, and `UNKNOWN` coverage. For the EPA pilot, `FULL` means both levels cover at least 99.5% of the requested line; `PARTIAL` means some but not all, including one resolved level when the other fails; `NONE` means a successful query found no line overlap with either Oregon layer; `UNKNOWN` means analysis could not produce a reliable conclusion. A successful query with zero features differs from a failed or absent dataset. Coverage is tracked per dataset dimension (`road-geometry`, `road-network-extract`, `road-discovery`, `epa-ecoregions-or-l3`, `epa-ecoregions-or-l4`, `wetlands`, `hydrography`, `occurrence`, `occurrence-inaturalist`, `occurrence-ebird`, `access-verification`), so a road-source failure can never appear as an ecological or access answer. The pilot's habitat and occurrence coverage remain `UNKNOWN`.

Geometry evidence and access evidence are different claims. `GEOMETRY VERIFIED` means road geometry comes from identified source data; `ACCESS UNVERIFIED` means Road Naturalist has not established public, legal, or practical access. A named road in a government centerline dataset is not an access finding, and the UI says so. Unknown source attributes stay `not provided` or `unknown` rather than being inferred.

Evidence kinds include `EXPECTED` (ecological prior), `HISTORICAL`, `RECENT`, `LOCAL` (precision supports a corridor), `MODELED` (deterministic output), and `INFERRED` (analyst interpretation). These are claim classes, not interchangeable strength grades. EPA Level III/IV ecoregions will be intersected with corridor geometry and used as context/prior, never proof of a local species record. iNaturalist and eBird adapters should return normalized records with source ID, taxon, observation time, quality, precision, provenance, ecoregion, and distance only where defensible. Obscured coordinates are stripped from normalized location and cannot produce a road-distance claim.

The Investigator researches sources, records contradictions, explains results, and challenges its own provisional findings. It must cite evidence and keep source facts, derived facts, findings, and interpretations distinct. It cannot invent GIS facts, occurrence records, coverage, or spatial scores, and every conclusion it reaches is produced by a named deterministic guardrail rule from cited evidence. A human may record a finding beside the automated one; a model may only annotate. Findings, coverage, contradictions, unresolved items, and freshness travel together in the portable bundle, so an exported result cannot be read without the reasons for it.

## Data plane and Cloudflare

Regional discovery now has a second, spatially aware catalog at `data/regional/manifest.json` (schema 2). It indexes versioned 0.2° grid cells for roads, NWI and NHD; `src/discovery/regional-catalog.js` selects road groups and 1 km halo cells, while `src/gis/service.js` verifies and registers their GeoParquet, deduplicates whole-feature replicas in SQL and runs the existing discovery batch. The catalog remains on Pages; regional Parquet is served directly from Road Naturalist's `data.roadnaturalist.com` R2 hostname. Localhost resolves the same paths from `./data/`. EPA's statewide Oregon files remain whole. The Investigator Worker has no R2 binding and performs no GIS compute. See [regional data](REGIONAL-DATA.md) for the decision, source window, build, failure behavior and measurements.

Current path: source GIS (EPA ecoregions, census road centerlines, USFWS wetlands, USGS hydrography) → offline Python preparation in `scripts/` → versioned GeoParquet and manifest → local static files → verified browser fetch and in-session buffer reuse → lazy DuckDB-WASM + Spatial corridor, road, ecoregion, wetland, and hydrography queries. The regional catalog already points to immutable R2 objects. Cells are spatial partitions for bounded transfer, while the corridor remains the domain unit. Manifests should describe bytes, SHA-256, schema, source vintage, coverage, and verified-empty results; they are validated per dataset type, and road datasets add source archives, road records, and the normalization method. Buffered habitat datasets additionally declare their recorded coverage extent, analysis-window margin, measurement CRS, and geometry treatment, because a coverage claim depends on knowing exactly which analysis region an extract covers. Live occurrence sources are not manifest datasets: they are APIs queried lazily, with per-source coverage (`occurrence-inaturalist`, `occurrence-ebird`) and an aggregate `occurrence` row derived from them, plus provenance recorded per analysis rather than per file. R2 CORS must allow the app origin and `Range` requests, and expose `Content-Range`/`Accept-Ranges`; validate this before release. Fruiting Forecast currently verifies full downloaded asset bytes; Road Naturalist should test actual range behavior before depending on partial reads. The current regional path reuses verified buffers for one browser session; persistent caching is future work if repeat visits justify it. User-owned research artifacts, if added, need an explicit retention/export policy separate from cache.

Cloudflare Pages serves the static application at `roadnaturalist.com` (project `roadnaturalist`), and the one Worker (`worker/`) answers at `api.roadnaturalist.com`. The Worker exists for exactly one measured reason: official county and agency sites send no CORS header, so the browser cannot read them. It is a fixed allow-list of declared sources with no client-supplied URL, no credential, and no passthrough body; a server-held secret (for example a future live-eBird key) would be the second reason. Both deploy from this repository with no build step (`npm run deploy:pages`, `npm run deploy:worker`), and [docs/DEPLOYMENT.md](DEPLOYMENT.md) is the topology and command reference. Offline ingestion is a build process, not a browser or Worker request. No D1 or account database is justified now; this is not a field-observation recorder. Keep secrets off the client and do not move deterministic corridor analysis to a Worker without a measured reason.

## Reference decisions

From **Fruiting Forecast**: keep static-first deployment, Leaflet's lesson that map is a replaceable view, DuckDB-WASM/Spatial and Parquet as a proven analytical path, immutable R2 data and digest-bearing manifests, bounded browser caches, explicit degraded/coverage states, deterministic scoring separate from optional AI, EPA ecological context, source provenance, and browser/Python testing. Its app currently concentrates UI, scoring, GIS, API clients, storage, and optional OpenRouter in `index.html` (927 dense lines); Road Naturalist keeps those as modules. Its square tiles and hunt/collecting domain are not adopted as Road Naturalist concepts. We also do not carry over its mushroom profiles, weather scoring, persistent DuckDB tables, analytics, or operational record database.

From the **Wildlife Road Cruise Investigator**: keep the sequence of geography → landscape → discovery → triage → road research → wildlife → verification → mapped geometry → ranking → QA, plus source registry, candidate rejection trail, unresolved questions, access checks, adversarial review, route guide, and portable JSON. Its `guide/routes/research` package is a useful export idea. Its current direct browser OpenRouter calls, local key, model-supplied component scores, neutral fill for missing scores, and single-file state/UI are not the authority model for Road Naturalist. Overpass-matched geometry is a useful verification technique, but partial/unresolved matches must remain explicit. The `fieldReports` placeholder in its export is not a Road Naturalist observation database.

## Next extension points

1. Widen the declared source catalog beyond the three pilot corridors and let a reviewer add a corridor's sources without editing code, keeping the probe contract (source, question, verbatim phrases, quoted windows).
2. Add the next habitat datasets by following the documented pattern in [docs/HABITAT.md](HABITAT.md) (pin, bound, normalize, coverage per requested region, provenance, fixtures, measured size).
3. Scale candidate discovery from the pilot window to a county or radius: partitioned road and habitat extracts, spatial pruning, row-group strategy, cached derived metrics — see the measured plan in [docs/DISCOVERY.md](DISCOVERY.md#scaling-what-would-have-to-change).
4. Consider one shared, explicit geometry-repair step for the corridors whose source geometry GEOS cannot buffer, so discovery and detailed analysis lift together instead of reporting UNKNOWN.
3. Add deterministic corridor metrics and score traces with coverage before connecting occurrence APIs or AI.
4. Replace the county+name road key with a road-level source ID when a state roadway inventory is adopted; the candidate layer already composes multiple roads.
5. Replace the pinned retired NHD HU8 extract with 3DHP once USGS offers a bounded, pinnable product or a responsive bounded service query; the habitat normalizer and queries already read canonical columns.
6. If a historical or seasonal occurrence layer is ever added, it belongs behind the same adapter boundary with its own coverage, provenance, and evidence kind (`HISTORICAL` vs `MODELED` vs `INFERRED`) — never merged into the recent public record.
7. Add the credential-backed eBird endpoint to the deployed Worker when live eBird evidence in the browser is wanted; the adapter contract already exists and the boundary is now proven in production.

The pilot corridor is real: geometry comes from pinned U.S. Census Bureau TIGER/Line 2025 road centerlines, EPA context from the real Oregon ecoregion extract, physical habitat context from pinned USFWS National Wetlands Inventory wetlands and USGS hydrography, and species occurrence evidence from the public iNaturalist and eBird APIs. Its access findings are qualified and dated rather than asserted: three pilot corridors currently report two restrictions and one partly covered probable public road, with every source, quote, contradiction, and unresolved item preserved. It still makes no habitat-quality, abundance, or likelihood claim, and none of the three is a recommendation.

Candidate discovery is real too: the same TIGER/Line vintage is extracted across the whole pilot window (5,300 features of the eligible classes), composed into 4,046 named road units, and proposed as 127 contiguous discovery corridors with measured road, wetland, hydrography, and ecoregion facts and explicit coverage. It ranks nothing and, before promotion, it knows nothing about access or species.
